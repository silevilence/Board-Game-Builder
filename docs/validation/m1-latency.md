# M1 操作等待诊断与优化验收

日期：2026-10-05。初次诊断基线 `bc6e86a`；实施优化基线 `05838d8`。以下先保留原始诊断，再记录优化与验收。

用户反馈 Windows Sandbox 内各项功能正常，但每次操作需等数秒。本机使用 Release 构建、quick-cards、种子 42、真人 p1，直接调用与 GUI 相同的 PlayerSession 路径。

## 复现

诊断程序保存在明确标记的本地调试目录 `.scratch/m1/perf/`，不作为正式回归测试或发行内容。

```powershell
dotnet run --project .scratch/m1/perf/Perf.csproj -c Release
```

最后一次运行：真人提交 458、523、461、478 ms；CPU 步进 1022、1010、699 ms。普通出牌加 CPU 回应最大 1545 ms，超过诊断预算 1000 ms，进程退出码 1；七次提交后正常终局。
另外两轮测量分别出现约 1.7 秒和 1.4 秒的出牌／CPU 往返。性能数值随负载变化，本机诊断门槛不代表通用硬件承诺。以上均未包含 GUI 中 CPU 步进后的 100 ms 等待，也不是沙箱内计时。

## 假设与实验

按优先顺序检查：每次 Lua 进程启动成本、操作内重复规则调用、UI 渲染或刻意延迟。

```powershell
dotnet run --project .scratch/m1/perf/Perf.csproj -c Release -- probe
```

相同空 Lua actions 脚本、相同输入：

| 路径 | 六次调用耗时（ms） |
| --- | --- |
| LuaWorker 进程隔离 | 308、237、248、232、217、217 |
| 直接 LuaEvaluator（仅诊断对照） | 75、0、1、0、0、1 |

每次 LuaWorker.Invoke 都启动并销毁 .NET 子进程，重复支付启动、装载和首次执行成本。真人提交执行规则判定和更新后的动作查询两次；普通 CPU 步进执行动作查询、CPU 决策、规则判定及更新后的动作查询四次，终局时少一次查询。一次普通出牌连同 CPU 回应累计六次进程调用，与测得等待量级一致。

没有 UI 的会话路径同样出现等待，排除画面渲染作为主要原因。PlayBoard.PumpCpu 额外延迟 100 ms，无法解释全部秒级等待。沙箱可能放大启动成本，但未在沙箱内计时，不把推断当作测量结论。

## 原始诊断结论

这是原实现的性能问题，不是简单卡牌规则必须等待的时长。用户随后要求完成性能优化，实施与验收以 ROADMAP 本地性能补充条目为准。

## 实现

- 每个 PlaySession 拥有一个延迟启动、串行处理请求的 Lua 工作进程。成功调用复用进程；每次调用依旧新建 Lua Script／全局环境及带种子的随机状态，不缓存席位动作或规则结果。
- 使用长度前缀 UTF-8 消息，读写前检查预算；请求源代码／输入预算不变。脚本错误、协议错误、超时或内存故障销毁工作进程，不自动重试动作。
- 保留每次调用 5 秒墙钟限制、64 MiB 托管堆限制和 256 MiB 私有内存监控。超时包括消息交换，非协作式昂贵计算可被父进程终止。
- 正常终局、对局故障、用户停止、窗口关闭、重开和批处理均释放工作进程。父宿主异常退出也使工作进程退出；成功调用达到 256 次后主动轮换。
- 移除图形 CPU 推进额外的 100 ms 固定等待。保留忙碌提示、不可重入提交和后台执行。
- 作者可监听 `BoardGame.Lua` ActivitySource 获取入口调用耗时；只带脚本路径／入口，不记录脚本正文、输入输出或隐藏状态。没有监听器时不创建活动。

## 性能回归与分阶段记录

正式回归入口：

```powershell
dotnet run --project tests/Engine.Tests -c Release -- latency
```

相同机器、quick-cards、种子 42、真人 p1，两次全新对局。先添加测试后运行旧实现：8 次真人操作（其中 6 次包含 CPU 回应）为 566.6、1413.7、1386.5、1119.2、433.8、1292.1、1310.1、1105.2 ms；1000 ms 预算检查失败。
最终代码完整回归测得 31.4、72.6、65.8、73.9、22.5、67.6、82.0、98.5 ms；预算检查通过，两局最终投影一致。

Lua 分阶段调用耗时由实际调用边界记录，包含 IPC；actions 数据也包含两局各自的一次冷启动：

| 阶段 | 调用次数 | 平均耗时 | 最大耗时 |
| --- | ---: | ---: | ---: |
| 规则动作查询 actions | 20 | 31.4 ms | 213.1 ms |
| 规则判定 decide | 14 | 11.8 ms | 16.0 ms |
| CPU 决策 decide | 6 | 11.3 ms | 13.4 ms |

本机预热后操作由秒级降至约 0.1 秒以内。首次开局仍需创建进程；不同机器和 Windows Sandbox 的绝对耗时可能不同，本次最终测量不冒充沙箱内性能数据。

原 `.scratch/m1/perf` 复现也已重跑：真人提交 33、24、23、23 ms，CPU 步进 48、45、61 ms，最长往返 84 ms，退出码 0；本轮实施前同一复现最长 1375 ms。

最终自包含发行物位于 `artifacts/player-release-perf-final`，可玩导出位于 `artifacts/quick-cards-perf-final`（双击 Play.cmd）。移除子进程 PATH 中的 dotnet 并将 DOTNET_ROOT 指向不存在目录，真实图形窗口完成两局和重开；8 次图形操作处理（含 CPU 回应）为 41.5、84.9、76.1、89.3、29.1、76.0、77.6、80.5 ms。
同一最终导出物的种子 1～20 全部终局、每局 7 次提交，独立重跑和回放一致。可提交的摘要见 [m1-perf-results.json](m1-perf-results.json)；完整 GUI／批量证据在 `artifacts/perf-validation/export-final-games.json` 和 `artifacts/perf-validation/batch-final/`。进程检查没有残留 Lua 工作进程。

## 回归与资源释放

Release 解决方案构建零警告、零错误；工程边界检查通过；16 组测试全部通过（新增 worker、latency，原 14 组继续通过）。
工作进程测试验证同 PID 复用、每次全新全局变量／闭包／随机状态、切换脚本不残留秘密值、并发请求不混淆、失败后恢复、外部进程崩溃后重建、256 次轮换和明确 Dispose。
昂贵字符串计算触发真实 5 秒墙钟超时并验证进程退出；执行中停止在 2 秒内完成；父宿主被强制终止后子进程退出；超大分配样例验证错误回收与恢复（不以此声称精确测出了内存阈值）。
PlayerSession 集成测试验证提交中 Stop 会取消并释放进程，不发布新帧、不残留 Busy，停止后的新提交被拒绝。

## Standards

独立审核没有发现明确规范违反或需处理的代码气味。发现并修复一项 P2：旧进程退出后释放对象但未清空引用，后续启动失败可能导致再次调用无法恢复。现在在启动替代进程前清空旧引用；复核无剩余阻塞。

## Spec

独立审核没有发现范围扩张或确定的实现错误。初审要求补充分阶段耗时记录；已通过 ActivitySource 和真实图形导出测试补齐。另补执行中停止与父宿主异常退出测试；复核无剩余代码阻塞。

本轮只优化本地脚本运行和生命周期；最终独立导出无控制台窗口仍按用户确认留在 M2 导出工作流。
