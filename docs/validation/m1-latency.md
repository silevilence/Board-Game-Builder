# M1 操作等待诊断

日期：2026-10-05。诊断基线 `bc6e86a`。本轮只测量与记录，没有修改运行时代码。

用户反馈 Windows Sandbox 内各项功能正常，但每次操作需等数秒。本机使用 Release 构建、quick-cards、种子 42、真人 p1，直接调用与 GUI 相同的 PlayerSession 路径。

## 复现

诊断程序保存在明确标记的本地调试目录 `.scratch/m1/perf/`，不作为正式回归测试或发行内容。

```powershell
dotnet run --project .scratch/m1/perf/Perf.csproj -c Release
```

最后一次运行：真人提交 458、523、461、478 ms；CPU 步进 1022、1010、699 ms。普通出牌加 CPU 回应最大 1545 ms，超过诊断预算 1000 ms，进程退出码 1；七次提交后正常终局。
另外两轮测量分别出现约 1.7 秒和 1.4 秒的出牌／CPU 往返。性能数值随负载变化，本机诊断门槛不代表通用硬件承诺。以上均未包含 GUI 中 CPU 步进后的 100 ms 等待，也不是沙箱内计时。

## 假设与实验

按优先顺序检查：每次 Lua 进程启动成本、操作内重复规则调用、UI 渲染或刻意延迟。

```powershell
dotnet run --project .scratch/m1/perf/Perf.csproj -c Release -- probe
```

相同空 Lua actions 脚本、相同输入：

| 路径 | 六次调用耗时（ms） |
| --- | --- |
| LuaWorker 进程隔离 | 308、237、248、232、217、217 |
| 直接 LuaEvaluator（仅诊断对照） | 75、0、1、0、0、1 |

每次 LuaWorker.Invoke 都启动并销毁 .NET 子进程，重复支付启动、装载和首次执行成本。真人提交执行规则判定和更新后的动作查询两次；普通 CPU 步进执行动作查询、CPU 决策、规则判定及更新后的动作查询四次，终局时少一次查询。一次普通出牌连同 CPU 回应累计六次进程调用，与测得等待量级一致。

没有 UI 的会话路径同样出现等待，排除画面渲染作为主要原因。PlayBoard.PumpCpu 额外延迟 100 ms，无法解释全部秒级等待。沙箱可能放大启动成本，但未在沙箱内计时，不把推断当作测量结论。

## 结论与后续

这是当前实现的性能问题，不是简单卡牌规则必须等待的时长。本轮没有以移除进程隔离来修复。
后续可评估受控工作进程复用和同一状态下动作结果复用，但须保持每次调用的新 Lua 状态、独立随机输入、超时终止、内存限制、故障后回收以及席位数据边界；不能直接改成宿主内执行脚本。
实施与验收以 ROADMAP 本地性能补充条目为准；当前问题仍未修复。
